## 2. The invariant monitor, completed — and a real defect

`utils/invariant_monitor.py` goes from four checks to seven. Six of the seven
invariants the plan asked for; the seventh is rejected in writing inside the file
itself (see §4).

### The finding: the Ultra Ball in flight counts as a prize

`_identify_prizes` reconciles by subtraction when the engine shows the whole
deck: `hidden = copies − hand − in play − discard`, and
`prize = hidden − the ones visible in the deck`. The reveal is triggered by
**playing a card**, and at that instant that card is in none of those zones: it
has left the hand and has not reached the discard. It counts as hidden, it is
not in the deck, and the subtraction files it as a PRIZE.

On the pinned board: the revealed deck has 46 cards and **three** of the four
Ultra Balls; the fourth is the one being played. The tracker ends up with
**7 cards in 6 prizes**.

This is not bookkeeping: `_gt_planes` and `_gt_wanted_basics` will not plan a
line whose card reads `ZONE_DECK == 0`, and the Meowth → Lillie's engine asks
the same question. Nor does it self-correct — each reveal fixes the previous one
and breaks the new one, so **there is always exactly one card the agent believes
it cannot draw**.

Pinned in `tests/test_the_ultra_ball_in_flight_becomes_a_prize.py` plus its
fixture: four green tests carrying the evidence and one `xfail(strict=True)`
holding the invariant. **The fix changes what the agent believes, so it has not
been made.**

## 6. ADDENDUM — the mutation gate was lying, and the two reasons

Written after the above, and it corrects the above. §3 said **8.6 seconds, 15
survivors and 6 ranges no test executes**, and said the Full Metal Lab fix had
landed unwatched. **All three figures were false**, and all three in the
direction that looks like a finding.

It came apart from the other end: the gate was reporting three survivors in
`ptcg/calc/damage.py` that a test in this very suite demonstrably kills.

### Cause 1 — a `settrace(None)` switched coverage off for everything after it

Three tests read a LOCAL variable of `agent()` by installing a trace function,
which is a legitimate and good technique. The problem was the cleanup:
`sys.settrace` to `None` does not *restore* coverage's tracer, it **removes**
it, and there is only one per thread. Line coverage recovers — only 0.8 points
were lost, which is why nobody saw it — but the dynamic CONTEXT does not:
**225 contexts for 1 843 tests, 11 test files out of 153**, all of them
alphabetically before `test_comfey_relief_against_bench_out.py`.

With that map, a line whose tests are missing comes back as "nobody watches it",
and a mutant run against the wrong tests comes back as a SURVIVOR. And it was
fast precisely because almost nothing reached the mutation stage.

Fixed in all three places (save `sys.gettrace()` and give it back) and guarded by
`tests/test_no_test_uninstalls_the_tracer.py`.

### Cause 2 — the probe was reusing stale bytecode

CPython validates a `.pyc` by mtime in WHOLE SECONDS and size in bytes. Two
mutants of the same file differ in neither: `meganium_active=False -> True` and
`neutralization_zone=False -> True` produce sources of identical length, and the
probe writes them milliseconds apart. The second run imported the first one's
bytecode.

This is not an odd corner: **every pair of boolean literals on a line has that
shape**, and so does every `>= -> >`. Any survivor count this project published
before today — the 46 from the night, the 16 from the re-sweep — is inflated by
this.

Fixed in `utils/mutation_probe.py`: the file's bytecode is deleted before each
mutant and the child runs with `-B`.

### The redesign: the contexts go away entirely

They are not fixed, they are removed. They cost 15+ minutes by construction (the
cost is the per-test context switch; narrowing `--cov` to a single file does not
reduce it), they have to be rebuilt every time the tests change, and **a stale
map does not look broken, it looks like good news**.

What replaces them is a single rule:

> **A KILL is reliable with whatever you ran. A SURVIVAL is only reliable
> against the whole suite.**

Each mutant runs first against a cheap candidate set (the test files that mention
the module or the identifiers on the new lines). Almost all die there, in
seconds, and that verdict is final. Whichever survives is re-run against
EVERYTHING before being reported. The cheap set can be as wrong as it likes: the
second step covers it.

### The honest result

| | With the context map | Redesigned |
|---|---:|---:|
| Survivors | 15 | **1** |
| "Uncovered" ranges | 6 | **0** |
| Time | 8.6 s (false) | **2 min 31 s** |

**The Full Metal Lab fix was watched after all**, wave-2 copies included. The
only survivor is **equivalent**: `meganium_active` is never read inside
`_our_effective_damage` (0 uses in the body, against 1 each for its two
neighbours), so flipping its default cannot change anything and no test can kill
it. It is a dead parameter that ~70 call sites still pass: removing it is a
signature refactor, and it has not been done.

### The lesson, which was already written down

This is the third time in two days that a detector in this project has reported
its own defects as the agent's: the differential oracle over three rounds, this
morning's `DECK_BELIEF` and `ENERGY_CAP`, and now the gate. The rule that works
is not the "validate the harness" doctrine, which was written down and failed
anyway: it is the **self-test that aborts the run**. The gate does not have one
yet, and that is the work it is missing.

## 8. The self-test that aborts, and the CI job

§6's lesson written into code. `utils/gate_mutation.py --self-test` runs the gate
against `utils/_gate_selftest/target.py`, a 12-line file whose verdict is known
in advance:

> it kills the **4** sites its companion test pins, and leaves exactly **1**
> alive — the default value of a parameter nobody reads.

Both halves, and the second is the one usually missing: a gate that cannot kill
reports everything as unwatched, and that reads as a pile of findings; a gate
that cannot leave anything alive passes any sensitivity check **without ever
finding anything**.

The target's two boolean literals are **on the same line and the same length on
purpose**: it is the exact shape that made CPython hand the second mutant the
first one's bytecode. If that fault returns, the self-test sees 2 survivors
instead of 1 and the run stops there.

**And the self-test is itself validated**, in
`tests/test_the_mutation_gate_refuses_to_run_when_it_is_broken.py`: with a
companion test that pins nothing it must **refuse**; unable to locate its own
blind spot it must **refuse**; and the file it mutates has to be left byte for
byte as it was. Four tests, 4 seconds.

It debuted by failing, moreover, and for the right reason: it looked for the
blind line by the parameter's name, which also appears in the target's
docstring, and resolved to a comment. It refused to run rather than guess.

**CI**: the `mutation` job in `gates.yml`, pull requests only, with the self-test
as a prior step. It is **non-blocking** on purpose — two versions of this gate
have already reported their own faults as findings, and a gate that jams the repo
with a false positive teaches people to ignore it. The `continue-on-error` comes
off once its output has been right a couple of times.

## 9. The `_identify_prizes` fix, and the number that decided it

The only confirmed defect of the agent still open. It is BEHAVIOURAL, so the
measurement rules.

### What changed

The card paying for the search is **in flight** and the subtraction was filing it
as a prize. The obvious version of the fix — "if it is the effect's card and
something does not add up, it is in flight" — **guesses**: from inside the loop,
a copy of the searcher sitting in a PRIZE is indistinguishable from one in
flight. Measured, that assumption was wrong **65 times in 26 280 boards**: it
moved the error instead of removing it, and left the deck one card short.

What does work is asking the **engine**: there are exactly `len(my_state.prize)`
cards face down. If the reconciliation has placed more, the belief is impossible
and the surplus is the one card we can name. An arbiter that can only fire when
something is demonstrably wrong cannot invent the opposite error.

| | Before | With the assumption | With the arbiter |
|---|---:|---:|---:|
| `DECK_BELIEF` (impossible prizes) | 3 281 | 0 | **0** |
| `DECK_BELIEF` (deck identity) | 0 | 65 | **0** |

Zero of both kinds over **26 617 boards judged**.

### What it cost in decisions: almost nothing, and that is the result

A two-tree recipe, because `--base REF` only swaps `main.py` and this fix lives
in `ptcg/` — with `--base` it would have come out 50% by construction. The
mandatory check was done:
`_identify_prizes.__globals__["__file__"]` points at different trees in each arm.

> **2 flips in 50 955 decisions (0.004%)**, with the base arm driving and the
> candidate seeing the same observation. 400 games.

At that frequency **you do not run a winrate gate**: two firings in 51 000
decisions cannot move a scoreboard above the noise, and the NEUTRAL that would
come out would be NEUTRAL by construction, not evidence of anything. It is the
same rule this project already had written down — measure the frequency before
the winrate — and the reason the night's report recommended not spending
self-play nights on rules that fire once a game.

**So why does it land?** Not for playing better, but because the belief was
**demonstrably impossible**: seven cards in six prizes. The golden corpus does
not move a decision either. What the measurement adds is the real size of the
effect, which is what stops it being sold as a play improvement.

The 2 flips have not been looked at one by one: at n=2 there is nothing to
conclude from them, and saying so is more honest than telling a story about two
boards.

## 10. T2.3, and one more monitor fault found while measuring

Four new properties in `tests/test_properties_of_any_legal_board.py`:
determinism, not writing over the observation you are handed, always a legal
index, never raises. **All four measured before being asserted** over 40 real
boards — determinism 40/40, non-mutation 40/40 — because a property is a claim
about the code, and asserting one that does not hold turns the suite red over
something nobody can act on. Soak: `PTCG_HYPOTHESIS_EXAMPLES=5000` runs all six
in 36 s.

**The plan's other seven candidates do not land**, and the reason is the one that
has been repeating for two days: they are MONOTONICITY claims — "a strictly
better board never gives a worse plan mode", "removing a threat never makes it
more defensive" — and each requires a judgement about what *better* means in this
game. That judgement is exactly what a property test exists to avoid needing, and
being slightly wrong produces a generator that reports correct play as a
violation.

### The collateral finding: 16 980 violations that were mine again

Measuring the prize property over fixtures turned up **1 of 40** that violated it
despite the fix. Checking it against real play versus the same deck, the monitor
returned **16 980 findings in 14 579 boards**, all of them saying "the tracker
believes 59 cards are left".

It was not the agent. `over_games(--opponent X)` deals **our** deck to seat 0 and
the opponent's to seat 1, but drives both with our agent — whose tracker
initialises with our 60 cards. Seat 1 holds a belief about a deck it is not
playing. In mirror mode both seats play our deck, which is why every earlier
measurement came out clean and why this was not seen until a fixture disagreed.

Fixed with `our_deck_seat()`, and the number of skipped decisions is printed.
Versus `alakazam.csv`: from 16 980 to **0**.

The prize property is **not** asserted over fixtures: replaying a mid-game board
cold makes `_first_turn_scan` treat the current hand as an opening hand, and that
1 of 40 fails for that reason, not because of the agent. That property lives in
the monitor, which does have the history.

## 11. T3.4: the flip-diff now runs on a clean checkout

The golden corpus was the only one of the four gates that did **not** run for
somebody who had just cloned: `records/` is local, transient data, so
`test_golden_corpus.py` skips — in exactly the situation where a reviewer most
wants to know which historical decisions a change moved. CI's own workflow said
so in its header.

**The corpus grew from 10 to 50 records** (`utils/record_corpus.py --games 50`,
against the real leaderboard decks piloted by the bot): 3 580 decisions.

**And it fits whole in git.** A record is the complete game, both seats, every
step: 50 of them are 41 MB. But the corpus only replays OUR decisions, so keeping
just those and compressing takes the same 50 games to **0.85 MB**. No sampling,
no argument about which games are representative: they are all there.

`utils/freeze_corpus.py` writes both halves, because one without the other is
worthless:

- `tests/corpus/frozen_records.json.gz` — the boards, with the **seat stored**
  rather than re-derived (`our_index` votes by counting visible cards from both
  seats, and this bundle deliberately throws away half of that input);
- `tests/corpus/frozen_decisions.json` — the snapshot to compare against.

**The two corpora are not redundant.** The local one **self-heals**: records are
transient, so a different md5 silently re-snapshots. The frozen one **cannot**
self-heal — git versions it, so its snapshot only changes when somebody commits
the change, and every flip is a flip. That is what makes it a gate rather than a
notebook.

Validated in both directions: with a flip injected into the snapshot it **fails
and shows the exact diff** (`golden: [999] ['NO']` / `actual: [1] ['NO']`); and
with `records/` hidden, the local one skips while the frozen one runs and passes.

A fault of my own along the way, from the same family that has been appearing for
two days: `comparar()` returns a tuple of four lists and I wrote `if flips:` — a
tuple of four empty lists is **truthy**, so the test failed over a corpus with
nothing wrong with it. Now it is unpacked and each of the four categories is
reported separately.

## 12. T4.1: the night, as a script somebody else can launch

The pipeline already existed — the runs of 6–7 and 8–9 August **are** this — but
it existed as a sequence of commands in somebody's terminal. A night only the
person who ran it can repeat is not infrastructure.

`utils/nightly.py`: suite → lint → corpus → coverage → mutation → oracle →
monitor → permutation → property soak → matrix. Three profiles: `--quick` (40 s,
"is the pipeline still working?"), the default (~1 h), `--full` (hours, with the
matchup matrix). One `REPORT.md` per run in `log/nightly_<stamp>/`.

The gates go first **and stop the night if they are red**: a run over a broken
tree attributes its own damage to the wrong stage.

### What is worth more than the wiring

The classification of each stage, which is these two days' lesson written into
code:

> A stage whose **self-test failed** is INVALID whatever its exit code —
> **including zero** — and its summary is **replaced** in the report instead of
> being shown.

A detector that cannot demonstrate it still works and on top of that says "I
found nothing" is the most misleading of the three outcomes, not the most
reassuring. An unvalidated number is not a smaller finding: it is not a finding.

And separately: a non-zero exit from the tools that **report through the exit
code** (the permutation probe, the mutation gate, the corpus) is FINDINGS, not
FAILURE. Calling what a tool finds a failure is how you teach people to ignore a
red pipeline.

Both rules are pinned in
`tests/test_the_night_quarantines_a_detector_that_cannot_validate_itself.py`,
including a check that the phrases `nightly.py` searches for are still the ones
the detectors print — a rename in any of them would turn every future INVALID
into a green OK, silently.
