## The headline: three defects nobody had read

All three were found by counting rather than by reading, which is the whole
argument of the plan.

### 1. A rule that is asked 61 619 times and never once fires

`_RULES_MEOWTH_FETCH[10] xerosic_alakazam` is **dominated**, not rare. Its
predicate is exactly `[9] xerosic_priority_over_boss` plus `win_via_boss`, and
the arithmetic hints at it: rule 9 is evaluated 62 072 times and fires 453; rule
10 is evaluated 61 619 — the difference, every single time — and fires **zero**.
The newer rule swallowed the older one's ladder, so the 1260/1200 split by
`strong_attacker` is never applied and everything lands on 9's flat 1310.

Confirmed by evaluating both predicates on every resolution rather than by
reading them, because "delete this rule" is a recommendation that has to be
earned:

    222 501 resolutions of _RULES_MEOWTH_FETCH over 900 games, three decks
    r9 false, r10 false   219 891
    r9 TRUE,  r10 TRUE      2 610
    r9 false, r10 TRUE          0     <- the only case where r10 could decide

Rule 10's predicate is never true alone. And the same table says rule 9's extra
guard is inert too: `not win_via_boss` never excludes anything, because the two
fire together every single time.

Alongside it: three separate `supporter_already_played` vetoes (LILLIE, BOSS and
XEROSIC play chains) asked 11 850–13 417 times each and firing never. In the PLAY
context that flag is never True when a Supporter is on the menu, exactly as in
the DISCARD context it is never False. One flag, two callers, degenerate in both
— the `93a27eb` family.

Instrument: `utils/rule_census.py` (`09b5432`).

### 2. The latch fires, and sixty lines later a general rule undoes it

`Lillie's Determination` is latched in the discard ladder — one copy protected at
2, the spare released at 72 — and then a card-agnostic block runs
`score = min(score, DISCARD_SUPPORTER_LIVE_KEEP)`, which is 2, for the Supporter
with the highest live value whenever another Supporter shares the hand. "The best
Supporter I could still play" is exactly as true of the second copy as of the
first, so the spare is re-protected and **the latch never reaches the menu**.

That is the general rule overriding its own special case, and it happens in four
different records — four times as often as the Meowth ex flip Wave 1 left
standing, which the same audit reproduces independently.

    12 duplicate pairs share a keep-band score across 118 discard menus
    Lillie's x4 · Meowth ex · Teal Mask Ogerpon ex · Meganium · Unfair Stamp

Instrument: `utils/duplicate_protection_audit.py` (`5716f30`).

### 3. Twelve menus of a hundred and eighteen pay with the fuel

The pending question — the cost of a search discarding the energy that fuels the

### 1b. A matchup rule that cannot be true in the chain it lives in

Chased from the census's own worklist, and this one is **structural** — provable
by reading, once the counter says where to look.

`_ESC_NS_RECUPERACION[20] tapu_vs_crustle` is evaluated 1 287 times in 2 400
games *against three Crustle decks* and fires zero times. Its predicate requires
`w.op_is_crustle_deck`. And the selector three hundred lines below reads:

    if ctx.op_is_crustle_deck or ctx.op_is_cornerstone_deck:
        best = _resolve_max(_ESC_NS_CRUSTLE, w)
    else:
        best = _resolve_max(_ESC_NS_RECUPERACION, w)     <- the rule lives here

The chain it sits in is the one chosen **when the opponent is not Crustle**. The
flag can never be true there. It is `_protect_last_supporter` again: not a rule
that misfires, a rule that cannot fire.

Nothing is lost by it: against Crustle the other chain covers the same recovery
through `basico_whitelist`, which lists Tapu Bulu and scores 900 — a higher tier
than the dead rule's 850. So the cost of this defect was never a bad decision;
it was a rule that reads like a live matchup answer and has never once been one.

### 1c. In matchup mode our agent never goes first — 0 of 60

Found while chasing another zero from the same worklist
(`_RULES_FOREST_PLAY[0] t1_going_first`: 11 920 evaluations, no fires). Measured
with the harness's own accounting:

    matchup mode (vs the bot)     candidate first [0, 0]    second [36, 60]
    mirror mode  (agent vs agent) candidate first [12, 30]  second [13, 30]

Two policies multiply. **Our agent always chooses to go second, deliberately** --
in `ptcg/turn/options/minor.py` the `IS_FIRST` YES option is `SCORE_VETO` and NO
scores 2, which is defensible under current rules, where the second player may
attack on their first turn. And **the bot has no rule for that select at all**:
it falls through to its generic branch, "the first `minCount` options", and the
first one is YES. So whoever wins the flip, the bot ends up first, every time.

This does not invalidate a winrate. It bounds its SCOPE, and the bound has never
been written down: the matchup matrix, the Crustle axis and **every gate run with
`--opponent`** — which is nearly all of them, including M1/M2 running tonight —
measure only the going-second half of the game. Against a real opponent that also
prefers going second we would go first about half the time, and that half has
never been played. Every branch reading `we_go_first == True` is code self-play
does not execute.

**And a latent defect in the same lines.** `AGENT_STATE.we_go_first` is assigned
while each option is SCORED, not when one is CHOSEN — YES sets it True, NO sets
it False — so its value is whatever the last-scored option wrote. It is correct
today by accident, because the menu happens to list YES before NO. Reverse that
order and the flag reads True while we go second, silently inverting every branch
that depends on it.

### 1d. And the half nobody had played is worth two and a half points

`OpponentBot(first_choice="second")` (`f077bff`) makes the bot decline, so the
coin flip decides — inside a single run, which makes the contrast randomised
rather than two populations compared. 800 games per deck:

    crustle_kangaskhan   79.00% first   68.00% second   +11.00
    marnie_grimmsnarl    94.25%         89.50%           +4.75
    alakazam             99.50%         99.25%           +0.25
    dragapult            98.00%         97.75%           +0.25
    cynthia_garchomp     98.75%         99.00%           -0.25
    festival_lead        98.50%         99.25%           -0.75

    AGGREGATE            94.67% (2272/2400)  92.12% (2211/2400)  +2.54
    SE ~0.72 pts -> 3.55 sigma (with this project's usual caveat: the z assumes
    an independence the bot does not honour, so read it as an optimistic bound)

Flat where the matchup is saturated at 99% — there is no room — and **it is worth
eleven points against the hardest deck we have**, which is where every point has
been fought for all week.

So the agent declines, every game, something worth eleven points in the matchup
it loses most. And it declines it while its opening rules are TUNED for the other
seat: every branch reading `we_go_first == True` has never executed, so this is
what going first is worth **unpolished**.

### 1e. And then the weighted matrix said no

The six-deck figure above is an **unweighted** average, and two of those six are
close matchups. Asked of the meta that actually exists — `matchup_matrix.py
--weights` over the 87 real lists, which is the only number that says "how we do
on the ladder" — it disappears:

    M8, bot always first, n=400   weighted 94.0%   prizes +3.853
    M9, coin decides,     n=300   weighted 94.0%   prizes +3.998

That pair is not comparable (different n, different runs), so a control was run
at matched n — same 87 decks, same 300 games, the flag the only difference:

                          weighted   unweighted   prize differential
    M10 bot always first    93.8%       91.5%          +3.882
    M9  coin decides        94.0%       92.5%          +3.998
                            -----       -----          ------
                            +0.2        +1.0           +0.116

**+1.0 point unweighted and +0.2 weighted, from the same games.** The unweighted
mean is 26 100 games per configuration, where an SE of 0.17 points makes +1.0
real; the weighted one cannot move because of what it is made of.

The two numbers say the same thing from two directions, and it is the one this
project keeps having to learn: **the gain is real and the meta does not contain
it.**
Going first is worth eleven points against Crustle, and Crustle is 2% of the
ladder. Thirty-one per cent of it is Marnie, where we already win 96–98% and
there is no room. The weighted winrate cannot move because the matchups it is
made of are saturated.

What did move is the **prize differential** (+3.853 → +3.998), which is the
metric with resolution where the winrate no longer has any — and which the
matched-n control will either confirm or take away.

So the honest framing for the morning is narrower than "+2.54 points": going
first is worth a great deal **where the games are close**, and the ladder is
currently not made of close games. It is a change to make for the hard matchups,
measured on the hard matchups — not a ladder-winrate play. This is
frequency-before-winrate applied to a finding of my own, four hours after the
same argument was applied to somebody else's.

## The linter learned the day's bugs

Three rules, one per defect that shipped on 10 August, none of which showed up as
a red test (`b9b25e9`):

* **R6** — a test that READS a `records/` file must carry a skip guard.
* **R7** — a `utils/gate_*.py` loading two arms must define AND call
  `provenance()`.
* **R8** — inside the DISCARD block the turn flags may only be read to build the
  horizon.

**R7 was not clean when it was written, which is the point of it.**
`utils/gate_promoted_relay.py` loads two arms, patches two seams by two different
routes — an attribute on the `retreat` module and an entry in the globals dict of
the module defining `_bench_finisher_upgrade` — and never asked whether either
patch had landed. `from ... import` binds a copy, so the attribute route reaches
only callers that go through the module object: rename either seam and the
neutralisation lands on nothing while the run prints a winrate. It now has a
`provenance()` that needs no board and refuses to measure when the arms agree.

## Two detectors caught their own authors

Worth recording separately, because it is the pattern the night was built on.

**The rule census failed its own self-test on the first run, and was right to.**
The specificity half reported a rule as having "decided" while the bands called
it dead. Both read the same counter and only one was right: in an ARGMAX chain
every rule that fires calls `value`, so a `value` call there is participation,
not decision. `Contadores.mando()` is the repair.

**Two audits disagreed about how many menus the corpus has.** The capture keyed
menus by `id(tc.select)` without holding a reference, and CPython reuses an
address the moment the object at it is collected: distinct menus landed on the
same key and merged. The same corpus reported 90, then 98. It is 118, and every
rate published before the fix had the wrong denominator. The value now holds the
select; three consecutive runs agree.

The general lesson, written into memory: **run a deterministic instrument two or
three times before believing a number it gives you.**
